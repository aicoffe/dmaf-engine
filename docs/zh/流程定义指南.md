# 流程定义指南（面向 dmaf 使用者）

> 语言：中文 | [English](../flow-definition-guide.md)

**适用：** dmaf v0.7.x。本指南随 `dmaf` 二进制分发（`dmaf new` / `dmaf new --dir .` 会复制到你项目的 `dmaf/docs/` 下）；中文真源为引擎仓库 `docs/zh/流程定义指南.md`，英文版见 `docs/flow-definition-guide.md`。
**读者：** 负责工作流定义（stage/scope）的流程作者。**定义的首选路径是让 AI 技能代劳**（见 §1「用 AI 技能生成定义」）；§2 起的字段语义与编译规则保留为参考——校对 AI 产出、排查编译错误或手工编写时查阅。

---

## 1. 五分钟上手

你的项目仓库里，dmaf 的内容收拢在一个定义层目录 + 一个运行层目录，与你的业务代码正交：

```
<你的项目>/
├── dmaf/                             # 定义层（入库）：dmaf 的全部"源"
│   ├── workflows/
│   │   ├── stages/<phase>/<slug>.md  # stage 定义（一件事怎么做）
│   │   └── scopes/<name>.md          # scope 定义（一个流程走哪些 stage）
│   ├── agents/                       # AI 资产：agent 定义
│   ├── skills/                       # AI 资产：skill 包
│   ├── hooks.yaml                    # 项目级 hook 配置（可选；文件头注释即配置示例）
│   ├── docs/流程定义指南.md           # 本指南（dmaf new 写入）
│   └── compiled/                     # 编译产物（dmaf 生成，入库，勿手改）
├── .dmaf/                            # 运行层（gitignore）：引擎独占的会话状态与审计
│   └── <会话目录>/                    # 引擎与 agent 都不要手工触碰
└── <业务目录>/                        # 工作流产出物：完整路径写在 stage 的 inputs/outputs（§4）
```

**分界线一句话：`dmaf/` = 你定义的（入库），`.dmaf/` = 引擎运行的（谁都别碰），业务产物 = 你项目的成果（你的版本控制决定去留）。**

只想用别人做好的流程？`dmaf add` 装包即可（官方实例：`dmaf add https://dmaf.aicoffe.com/aicoffe/dmaf-sdlc`），无需通读本指南。要定义自己的流程，同样不必从手写开始——优先让 AI 技能代劳（下节），字段细节留作参考。

### 用 AI 技能生成定义（推荐）

编写 stage/scope 定义不需要逐字段手写。harness 里部署了定义技能 `create-workflow`，用自然语言触发即可，它按你的输入自动选模式：

| 模式 | 适用场景 | 触发示例 |
|---|---|---|
| 问答式（默认） | 零星变更：新增一个 stage、新建一个流程（scope）、给流程加审批门 | "给现有流程加一个风险评审 stage，读 spec 草案，产出风险评审记录，挂人工门" |
| 文档式 | 已有成文的流程定义文档（阶段 / stage / 输入输出 / 评审门 / 角色表），整体转成 dmaf 定义 | "把这份流程文档转成 dmaf 定义" |

技能的工作方式：采集业务意图（问答式一次问齐；文档式以文档为唯一事实源、只对真正含糊处集中问一轮）→ 按模板生成 `dmaf/workflows/` 下的定义文件（样板字段、编译约束、成员与顺序自动填好）→ 与你确认后执行 `dmaf compile` 验证，编译错误自行修复。你的职责是回答业务问题（或提供文档）、审阅生成结果、提交 `dmaf/compiled/`。

前置：技能已部署到 harness。`dmaf new` 已把技能随骨架写入项目 `dmaf/skills/`（引擎内嵌下发），`dmaf install --harness <name>` 部署到 harness 后即可触发；通过 `dmaf add` 装包进入、没跑过 `dmaf new` 的存量项目，跑一次 `dmaf new --dir .` 补齐。技能是引擎槽位，不随工作流包分发。技能缺失时也可手写定义：§2 起的参考章节就是为此保留的。

日常闭环（定义或资产变更后按序执行）：

```bash
dmaf compile                # 定义 → 编译产物；全部结构校验在此把关
dmaf compile --check        # 漂移守卫：确认入库产物与源一致
dmaf install --harness opencode   # AI 资产部署到 harness（账本哈希门：未改动自动更新，用户改过跳过并报告）
dmaf check --harness opencode         # 工作流引用 vs harness 实际内容（无输入选择器时默认标准布局）
dmaf doctor --harness opencode    # 日常自检：布局/产物漂移/清单 engine 兼容/引用齐备性/资产漂移
```

修改定义后只需重跑 `dmaf compile` 并提交 `dmaf/compiled/`（产物字节确定，diff 即评审）。`dmaf compile` 等命令的默认路径即上图的 `dmaf/…` 位置；`dmaf check` 无输入选择器时默认标准布局（`dmaf/workflows/{stages,scopes}`），一般无需显式传参。日常自检动线：git pull 后 `dmaf doctor --harness <name>`——`would_change` 重跑 install 即同步；`modified` 为用户改过的目标，确认后加 `--force`。

### 内联 vs 标准目录

两种写法共享同一套解析与语义，按规模选择：

- **标准目录**（`dmaf/workflows/stages/` + `scopes/`，经 `dmaf compile`）：需要 scope 复用、成员治理、编译期评审、产物 diff 评审的流程——**演进中的正式流程一律用这个**；
- **内联单文件**（`dmaf start --workflow <yaml>`）：原型/试验/极小流程的语法糖。不做产物化、不进 scope 网格；新语义自动获得内联支持（与标准目录共享解析器）。
- 内联与标准目录**共享同一解析器**，等价性由引擎测试的合成夹具持续守护（仓库样例为 scope-only，无内联定义）。

## 2. Stage 定义

> **本节至 §8 是参考章节**：AI 技能（§1）生成定义时会自动遵守这些字段约束与编译规则；这里的内容用于校对技能产出、对照编译错误表排错，或在没有定义技能时手工编写。

### 2.1 文件与命名

`dmaf/workflows/stages/<phase>/<slug>.md`——YAML frontmatter 声明结构，正文写执行说明（供人读，也作为 agent 的背景上下文）。

两条硬规则：**`id` 必须等于文件名 stem**；**`phase` 必须等于所在目录名**。放错即编译错。phase 是纯分类标签，不参与路由。

### 2.2 frontmatter 字段表

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✓ | stage 唯一标识，= 文件名 stem |
| `phase` | ✓ | = 所在目录名 |
| `collaboration` | ✓ | `single`（恰好 1 个 agent）\| `sequential` \| `parallel`（≥2 个 agent） |
| `agents` | ✓ | 工作者清单，见 2.3 |
| `retry` | — | `max_attempts`（首次尝试**之后**的重试上限，`1` = 共 2 次）、`on_exhausted: abort_workflow \| continue`，缺省 1 / abort |
| `approval` | — | `required: true` 时必须给 `gate`（门名）；成功后停在 `awaiting-approval` 等人批复 |
| `execution` | ✓ | `always` \| `conditional`（conditional 的跳过语义见 §4） |
| `on_skip` | — | `skip`（默认）\| `run`：硬输入生产者被跳过时，本 stage 传递跳过还是照常派发（§4 跳过语义） |
| `inputs` / `outputs` | — | 在 agents 项内声明（完整路径模板），见 §4 |

**stage 文件不得写 scope 字段**——"这个流程包含哪些 stage"住在 scope 文件里。

### 2.3 agents 项字段

```yaml
agents:
  - agent: architect                # agent 名，须存在于 harness（agents/ 资产）
    skills: [architecture-analysis]  # skill 名列表，可为 []
    inputs:                        # 输入工件完整路径：字符串=硬依赖；映射可声明 required: false（软输入）
      - "deliveries/{SESSION_ID}/spec/{topic}-spec草案.md"
    watches: ["notes/{topic}-背景资料.md"]   # 软依赖（阅读兴趣）：解析进指令 payload，缺失容忍，不影响拓扑
    outputs: ["deliveries/{SESSION_ID}/design/{topic}-hld.md"]
    task_description: "基于 spec 草案，产出架构设计与ADR"   # 支持 {变量} 模板；用户原始输入仅由首个 stage 经 {TASK} 承接，下游只消费上游工件
    vars: [product_line]           # 可选：从会话变量集（含常量）显式挑选子集，平铺进 action 的 vars 字段
```

约定：**outputs 是承诺**——report 时 Engine 校验文件存在，缺失即按失败处理；**用户原始输入只进流程入口**——保留变量 `{TASK}` 仅由首个 stage（intent-capture 类）的 `task_description` 承接，下游 stage 一律消费上游工件，不引用 `{TASK}`，业务短名仅作产物文件名前缀；无输出工件的 stage（如"提交到外部系统"类）`outputs: []`，以 agent 的回报为准。产出格式（markdown/json/pptx 等）由 skill 的执行说明约定（skill 是 agent 行为的唯一事实源），协议不携带格式字段。

### 2.4 完整示例

```markdown
---
id: architecture-analysis
phase: design
collaboration: single
agents:
  - agent: architect
    skills: [architecture-analysis]
    inputs: ["deliveries/{SESSION_ID}/spec/{topic}-spec.md"]
    outputs: ["deliveries/{SESSION_ID}/design/{topic}-hld.md"]
    task_description: "基于 spec，产出架构影响声明、设计与 ADR 草案"
retry:
  max_attempts: 1
  on_exhausted: abort_workflow
approval:
  required: true
  gate: architecture-review
execution: always
---

# 架构设计

基于 spec 产出架构设计。

## Steps

1. 读取 spec 与既有架构基线。
2. 产出架构影响声明、设计与 ADR 草案。
3. 等待审批门 `architecture-review`。
```

## 3. Scope 定义

`dmaf/workflows/scopes/<name>.md`——**成员认领 + 流程级元数据**。stage 不被任何 scope 认领就是惰性的（编译进图、不进任何流程，编译器打 advisory）。

硬规则与 stage 对称：**`name` 必须等于文件名 stem**，放错即编译错。

```markdown
---
name: sdlc-standard
description: 需求→设计→开发三阶段流程
vars:                                # 业务变量声明（mapping 形态：名 → 内联默认值）
  topic:                             # 空值 = 必填（start 必须提供）
  constraints: ""                    # 字面值 = 可选，内联默认
constants:                           # 常量：字面值，模板可引用，恒取定义值（--var 拒收）
  product_line: "课件"
completion_template: |              # 可选：交付文案模板（§3.1）
  全部完成！主题：{vars.topic}
  产出物：{outputs.spec-generation}
include_stages:                     # 成员认领（唯一事实源）
  - intent-capture
  - spec-generation
  - …
---

# 正文：流程说明（人读）
```

**两条强制规则：**

1. **`include_stages` 顺序即执行序**（引擎按序列顺序严格串行推进，一次一个 stage）；硬输入的生产者必须是成员且排在消费者之前——顺序违反数据依赖 = 编译错；
2. 引用不存在的 stage、重复条目 = 编译错。`depends_on` 字段已移除：stage 间的"谁先谁后"由本序列表达，"谁给谁供数据"由硬输入完整路径表达（数据依赖边由引擎自动推导）。

### 3.1 交付文案模板（`completion_template`，可选）

工作流走到 `complete` 时，Engine 按此模板渲染 `payload.completion_text`，Orchestrator **原样展示**——交付文案由定义声明而非编排 prompt 背诵。语法（专用渲染器，与 §4 的工件模板不共用）：

| 占位符 | 渲染为 |
|---|---|
| `{vars.<name>}` | 会话变量（含常量），name 必须已声明 |
| `{outputs.<stage_id>}` | 该 stage 全部 agents 的产出路径，"、" 连接；stage_id 必须在 `include_stages` 内 |
| `{{` / `}}` | 字面花括号 |

规则：

- **刻意不支持条件与循环**——呈现模板不做逻辑；失败明细由 `payload.summary.failed_actions` 结构化给出，Orchestrator 机械转述；
- 占位符引用未声明的变量或非成员 stage = **编译错**（内联 workflow 同语义，`dmaf validate` 把关），因此渲染期不会缺键；
- 不写该字段 = complete 指令不携带 `completion_text`，Orchestrator 退回转述 summary。

## 4. 工件与模板变量

- 工件在定义里写**完整路径模板**（项目根相对，支持变量），Engine 在派发时渲染：`deliveries/{SESSION_ID}/design/{topic}-spec.md` → `deliveries/20261022-153000/design/课件-spec.md`。渲染后仅对最后一段（文件名）做非法字符清洗，目录段原样保留。
- **产物路径是业务语义**：写你项目的业务路径；常用 `dmaf-output/{SESSION_ID}/<子目录>/`（固定前缀 dmaf- 避免与用户自定义目录冲突；工作成果须入库，引擎不会把它写进 .gitignore） 按会话分桶（一次会话的产物聚在一个目录，重跑互不覆盖；`dmaf fork` 分叉出的会话同样各有其桶）。**不要写进 `.dmaf/`**——那是引擎独占区（会话状态与审计）。跨 stage 传递的工件：消费者 inputs 的路径模板渲染后与生产者 outputs 的渲染结果**相同**即形成生产者-消费者关系（按完整路径精确匹配，同名不同目录是不同工件）；无生产者的输入即外部产物，路径原样使用。单 stage 内的临时文件由 skill 自理（如系统临时目录），不进 delegation 协议。
- **变量规则**：模板变量必须 ∈ **scope 声明集**（`vars` ∪ `constants` 名）∪ **引擎保留变量**。编译期按全 scope 声明并集把关，未声明的变量直接编译错。常用业务变量（`topic`、`knowledge_point`、`constraints` 等）由 `dmaf start --var` 提供、scope `vars` 声明。

**引擎保留变量**（无需声明，机制内注入；引擎内置仅此两个）：

| 变量 | 说明 |
|---|---|
| `SESSION_ID` | 会话 ID（时间戳字符串，**每次渲染活绑定**为当前会话目录名；不是路径，常用于产物路径按会话分桶或派生唯一标识，如 `dmaf-output/{SESSION_ID}/…`、`course_{SESSION_ID}`）。`dmaf fork` 分叉出的会话有自己的 ID，产物桶随之切换，分叉点前的产物由引擎复制到新桶 |
| `TASK` | 用户需求原文（`start --task` 提供时注入；工作流以它承接自然语言输入，提取归首个 LLM stage） |

**会话变量的合成**：声明类别只有两种——业务变量（scope `vars` 声明）、**常量**（scope `constants` 声明），外加保留变量（上表）。`dmaf start` 时 Engine 按下序合成为**一份**会话变量集，stage 工件模板、`task_description`、delegation 变量平铺与 §3.1 的 `{vars.*}` 全部共用这一份：

1. `constants` 常量（字面值，恒取定义值）；
2. `vars` 内联默认值；
3. `--var k=v` 提供值（**仅接受 `vars` 声明的名字**，覆盖同名内联默认）；
4. 保留变量 `SESSION_ID`（总是注入，且每次渲染都活绑定为当前会话 ID——fork 后自动指向新会话）、`TASK`（非空时注入）。

必填变量 = `vars` 中空值且 start 未提供的名字，缺失即拒绝启动（退出码 3，报 `缺少必须变量`）。业务短名（如样例的 `topic`）在 stage 里承担产物命名，与承载需求原文的 `TASK` 分工不同。`--var` 引用常量报 `常量不可通过 --var 覆盖`；两类声明（`vars`/`constants`）名字**互斥**且不得占用保留名，违规 = 编译错。`derived_vars` 已移除——固定字面值用 `constants`，组合值由模板直接引用变量组合（如 `"{product_line}-{SESSION_ID}"`）。

- 同名输入/输出模板精确匹配即形成**生产者-消费者关系**；**硬输入**的生产者必须是所在 scope 的成员且排在消费者之前（编译期校验，数据依赖边由引擎自动推导，无需声明）；生产者不在成员中（轻流程裁剪某条设计链）时必须改软引用。
- **软输入**（`{ artifact: …, required: false }`）与 **`watches`**（阅读兴趣）不做闭包要求；已知缺失的输入会列入指令 `missing_inputs` 字段（advisory）。
- **委托报文（`delegation`）由 Engine 预构造**：dispatch 指令的每个 action 自带现成的委托 JSON，Orchestrator 原样转发给 subagent，不做任何拼装。**路径字段与 stage 定义同名**（`inputs`/`outputs`，值即名称模板解析后的完整路径，恒在、空数组表示无——单产出 stage 的唯一路径即写入目标），因此定义里声明的就是 agent 收到的，无需记忆第二套词表；其余协议字段为 `role`/`task_description`/`revision_feedback`（仅修订轮出现）。流程变量按**会话 vars 全集（含常量）∪ 该 agent `vars:` 声明集挑选的子集（进 action 的 `vars` 字段）**平铺为顶层字段——常量出现在会话报文里；与同名变量冲突时以协议字段为准。上游处理结果需要被下游消费时，走 `inputs`/`outputs` 工件（文件即承诺），不设摘要类特殊变量。字段集由引擎固化（不随 stage 配置），规范见 `docs/schemas/delegation.schema.json`，样例 agent（`dmaf/agents/*.md`）即协议的活示例。
- **跳过语义**：agent 回报 `status: skipped`（须附非空 `reason`）→ stage 记 `[S]`；硬输入生产者被跳过的下游 stage 默认**传递跳过**（逐级审计），`on_skip: run` 可豁免；`execution: conditional` 是"可能跳过"的声明性标注（硬输入生产者不可为 conditional-only，编译期拦截）。`skipped` 是已消解终态：被跳过的 stage **不阻塞流程推进**——"按需" stage 写进 scope 序列表达先后，下游以软输入引用其产物（缺席进 `missing_inputs`）；同 stage 内 sequential 前序 agent 的产物由后序 agent 软引用交接（合法，死接线检查豁免自身 stage）。

## 5. 审批门与修订轮

`approval.required: true` 的 stage 完成后停在 `awaiting-approval`：

```
生成完成 → awaiting-approval → 人批准(granted) → completed → 下游
                             ↘ 人拒绝(rejected) → revising → 自动重新派发
                                 （修订派发携带 revision_feedback = 拒绝备注，轮次不限）
```

gate 名按约定在流程内唯一（引擎不查重——它是对人与 agent 标识「哪道门」的名字，如 `outline-review`）。修订轮由 Engine 自动编排：拒绝后下一次 `next` 会带回 `revision_feedback` 重新派发同一 agent。
**评审者（可选）**：`approval.reviewer: <agent>` 把批复交给指定 agent 先行评审——`await_approval` 指令会携带评审者与其应审阅的产出物清单，Orchestrator 派发评审者后以其结论发 approval report；审计分片记录 reviewer 溯源。缺省（不写 reviewer）即人工批复。

## 6. 重试与并行聚合

- `max_attempts` 是**首次之后**的重试上限；失败时 Engine 记 `retry.scheduled` 审计并在下一跳自动重发（新 action_id，attempt+1）。
- `on_exhausted: continue` 的 stage：重试耗尽后不阻断工作流，下游输入不剔除缺失项（缺失工件由下游自行处理）。
- **并行/顺序聚合**：以每个 agent 最后一次尝试为准——重试成功即抹平早先失败。

## 7. 工作流模式支持与设计取舍

Engine 的执行模型是刻意收窄的代数——四种机制组合出全部表达力：

| 机制 | 语义 |
|---|---|
| 序列串行推进 | scope 成员按 `include_stages` 序列执行（**顺序即执行序**），**一次只派发一个 stage**，在途 stage 阻塞后续——引擎没有 stage 级并行 |
| stage 内编排 | `collaboration: sequential / parallel`：并行只发生在 stage 内部的多 agent 之间（聚合规则见 §6） |
| 按需消解 | `execution: conditional` 自评跳过 + 传递跳过（§4）——运行期实际推进的是编译期图经跳过消解后的剩余序列 |
| 门修订回路 | 拒绝 → revising → 携 `revision_feedback` 重派（§5），仅限本 stage 内重入 |

**常见工作流模式对照：**

| 模式 | 支持 | 表达方式 |
|---|---|---|
| 线性流水线 | ✓ | 拓扑序即流程 |
| 按需分支（某环节可能不适用） | ✓ | conditional + `skipped`：审计留痕、按需跳过不设门 |
| 互斥路由（两条互斥路径各有下游） | 弱 | 无图级分支机制：合并进单个 stage 由 agent 内部判断——分支决策交给 agent，结构对引擎保持唯一 |
| 独立工作的并行推进 | 有限 | 合并进同一 stage 的并行 agents（共享门与重试策略），或串行化；无 stage 级并行 |
| 集合扇出（逐任务/逐模块处理） | ✓（吸收式） | 拆解 stage + 执行 stage 内部逐项循环（样例即 task-breakdown → atomic-execution）；审计粒度到 stage，任务级过程留痕在产物文档 |
| 单点修订迭代 | ✓ | 门修订回路 |
| 跨阶段迭代（缺陷→修复→重测） | ✗ | 刻意不支持：追加式审计无回边。缺陷如实进报告交门（如 `pr-review`）由人裁决，代码修复走下一轮会话或 `fork`（审计天然分轮） |
| 人工在环 | ✓ | 任意 stage 可设审批门 |
| 事件/定时触发、动态结构、子流程嵌套 | ✗ | 域外：编排是 pull 式的，每一步 `next` 都是纯函数 |

**取舍的根**是三条引擎原则，它们决定了表达力的形状：

1. **确定性**——`next` 是纯函数（禁时钟/随机/IO）：图越笨，`verify-determinism` / `replay` / `fork` 越便宜（线性推进下分叉点至多一个在途 stage，分叉语义平凡）；
2. **审计优先**——追加式哈希链不可改写，因此没有跨 stage 回边、没有 completed→revising 的全局重入；
3. **复杂度分层**——结构的确定性留给引擎（线性推进 + 固定聚合规则），判断的噪声交给 agent（内部循环、互斥判断、`skipped` 自评）。stage 是审计单元：往 stage 里吸收越多迭代，审计粒度越粗——这是刻意交换，且方向正确。

**流程作者的判据**：需求能分解进上表四层机制，就用定义表达；不能分解的先问是否属于本域（AI-native SDLC 类确定性交付流程）。样例库即合模范本：hifi-ue 与 architecture-analysis 按数据流本可并行，样例选择串行（UE 先行喂架构判断）；detailed-design 把前后端两份 lld 合成一个并行 stage 共享一道门。拿不准时优先选"合并 stage / 串行化 / 新会话分轮"，而不是依赖引擎新增控制流。

## 8. 编译错误对照表

| 错误信息（节选） | 修法 |
|---|---|
| `工件模板 '…' 引用未知变量 '{x}'` | 变量未声明：加进 scope `vars`（或为常量/派生/保留变量，§4） |
| `stage 'X' 的输入 '…' 没有任何 stage 的 outputs 能提供` | 无生产者：补一个产出的 stage；外部既有文件改软输入引用（`required: false`） |
| `stage 含 depends_on 字段（已移除）` | 执行顺序写进 scope 的 include_stages 序列，数据依赖由硬输入完整路径表达（生产者自动推导） |
| `…的硬输入 '…' 的生产者 'Y' 不在成员序列中` | 把 Y 纳入 scope 成员并排在消费者之前，或把该输入改为软引用（`required: false`，按需裁剪形态） |
| `…的生产者 'Y' 均排在 stage 'X' 之后——生产者必须排在消费者之前` | 调整 include_stages 顺序：生产者排在消费者之前（顺序即执行序） |
| `…的软输入 '…' 的生产者 'Y' 排在其后——…（死接线）` | 线性执行序下该输入本会话永远缺席：调整顺序，或改由非成员/外部提供 |
| `…由本 stage 自己生产（疑似定义错误）` | 输入输出同名，改掉 |
| `stage id 'X' 与文件名 stem 'Y' 不一致` | 改 id 或改文件名 |
| `phase 'X' 与所在目录 'Y' 不一致` | 移到对应目录或改 phase |
| `stage 'X' 声明了 scopes` | 删掉；成员写进 scope 文件的 include_stages |
| `completion_template 占位符 '…' 引用未声明的变量/stage '…'` | 变量加进 scope vars/constants，或 stage 加进 include_stages（§3.1） |
| `scope 'X' include_stages 条目 'Y' 在 stage 库中不存在` | 改 slug 或先建 stage 文件 |
| `stage id 重复` | 改 id（序列无环：执行顺序 = include_stages 书写顺序） |
| `collaboration=single 时 agents 必须恰好 1 个` | 删到 1 个或改 collaboration |

## 9. AI 资产（agents / skills）

- `agents/<name>.md`：frontmatter `name`（唯一）、`mode`（`primary` | `subagent` | `all`——工作流只能引用 `subagent` | `all`，`primary` 不可派发，`check` 校验）、`description`（非空）；正文写职责与约定。
- `skills/<name>/SKILL.md`：frontmatter `name` 必须等于目录名；可附带 `scripts/` 等资源。
- 部署与校验闭环：

```bash
dmaf install --harness opencode     # 标准目录 → harness（账本哈希门，见下）
dmaf check --harness opencode       # 工作流引用 vs harness 实际内容（无输入选择器时默认标准布局）
```

`--harness` 接名称，由引擎解析为项目根下的目录：`opencode`→`.opencode`、`claude`（别名 `claude-code`）→`.claude`、`zcode`→`.zcode`、`cursor`→`.cursor`、`gemini`（别名 `gemini-cli`）→`.gemini`；`codex`→`.codex`、`dsh`→`.dsh`（这两个布局的 agent 会自动转换为 TOML）。形如路径的值（含分隔符或 `.` 开头）按 flat-md 布局透传，未知裸名报错（退出码 2）。

**install 是账本哈希门语义**：harness 目录根的 `dmaf-installed.yaml` 记录引擎写入每个目标时的指纹——目标缺失即安装（installed），未改动的随源升级**自动更新**（updated），用户改过的**跳过**并报告（skipped），`--force` 显式覆盖（overwritten）。`--prune` 清孤儿——凡名字不在包源里的条目一律清扫（按名单判定而非账本），本地手放的技能目录会被删，慎用；`--check-only` 只读体检。

- 引用清单里**没有**的 agent/skill（如 scope 化样例中的 sdlc-*）会由 `check` 列出——那是部署期提示；运行期 skill 缺失属于执行错误：agent 失败 → report failed → 修复 harness → 对同一 `--session` 重新 `next` 续跑。

## 10. 端到端最小示例

以"给现有流程加一个风险评审 stage"为例。走 AI 技能时，对 `create-workflow` 说一句"加一个风险评审 stage，读 spec 草案，产出风险评审记录，挂人工审批门"即可——它会生成文件、反推成员与序列位置并跑编译；下面的手写步骤展示的是它替你做的事：

1. 新建 `dmaf/workflows/stages/design/risk-review.md`（inputs: spec 草案，outputs: 风险评审记录）；
2. 下游 stage 把它的 outputs 加进 inputs（数据依赖由输入表达），并在 scope `include_stages` 序列中把它排在消费者之前；
3. `dmaf compile` → 通过后提交 `dmaf/compiled/`；
4. `dmaf check --harness <name> …` 确认引用的 agent/skill 已部署；
5. 运行会话，新 stage 出现在计划中。

## 11. 命令速查

| 命令 | 何时用 |
|---|---|
| `dmaf new [--dir .]` | 项目一次性：补齐标准布局（绝不覆盖已有文件） |
| `dmaf compile` / `--check` | 每次改定义后；产物 diff 即流程变更评审 |
| `dmaf install --harness <name>` | 每次改 agents/skills 后 |
| `dmaf check --harness <name>` | 部署后 / CI：工作流引用 vs harness 实际内容（缺省标准布局） |
| `dmaf doctor --harness <name>` | 日常自检：布局/漂移/清单兼容/引用齐备/资产漂移 |
| `dmaf start --scope <名>` / `dmaf start --workflow <f>` | 启动会话 |
| `dmaf next / report` | 编排循环 |
| `dmaf inspect / log / verify-audit / replay / fork / cancel / verify-determinism` | 会话运维 |
| `dmaf validate --workflow <f>` | 内联工作流结构校验 |
| `dmaf add --from <源>` / `dmaf push <目标>` | 安装 / 交付工作流包（同一合并核心；add 也接 market 条目 URL） |
| `dmaf auth login / logout / status`、`dmaf publish` | market 登录态与发布 |

深水区（均在引擎仓库，`dmaf new` 不随指南分发到用户项目）：引擎手册（命令细节，`docs/engine-manual.md` / 中文 `docs/zh/引擎手册.md`）、`docs/zh/phase、stage、scope定义.md`（本仓库样例清单）。
