# Flow Definition Guide (for dmaf users)

> Language: English | [中文](zh/流程定义指南.md)

**Applies to:** dmaf v0.7.x. This guide ships with the `dmaf` binary (`dmaf new` / `dmaf new --dir .` copies it into your project's `dmaf/docs/`); the Chinese source of truth is the engine repo's `docs/zh/流程定义指南.md`, and this English edition is `docs/flow-definition-guide.md`.
**Audience:** workflow authors responsible for workflow definitions (stage/scope). **The preferred route for authoring definitions is to let the AI skill do it** (see §1 "Generate definitions with the AI skill"); the field semantics and compile rules from §2 onward are kept as reference — consult them when proofreading AI output, debugging compile errors, or hand-writing definitions.

---

## 1. Five-minute quick start

In your project repository, dmaf's content is gathered into one definition layer directory plus one runtime layer directory, orthogonal to your business code:

```
<your-project>/
├── dmaf/                             # Definition layer (committed): all of dmaf's "sources"
│   ├── workflows/
│   │   ├── stages/<phase>/<slug>.md  # stage definition (how one thing is done)
│   │   └── scopes/<name>.md          # scope definition (which stages a workflow walks)
│   ├── agents/                       # AI assets: agent definitions
│   ├── skills/                       # AI assets: skill packages
│   ├── hooks.yaml                    # project-level hook config (optional; the file-header comment doubles as the config example)
│   ├── docs/流程定义指南.md           # This guide (written by dmaf new)
│   └── compiled/                     # compiled artifacts (generated by dmaf, committed; never hand-edit)
├── .dmaf/                            # Runtime layer (gitignored): engine-exclusive session state and audit
│   └── <session-dir>/                # neither the engine nor agents: never touch by hand
└── <business-dir>/                   # workflow deliverables: full paths written in stage inputs/outputs (§4)
```

**The boundary in one sentence: `dmaf/` = what you define (committed to the repo), `.dmaf/` = what the engine runs (nobody touches it), business artifacts = your project's deliverables (your version control decides whether they stay).**

Just want to use a workflow someone else already built? `dmaf add` installs the package (official instance: `dmaf add https://dmaf.aicoffe.com/aicoffe/dmaf-sdlc`) — no need to read this guide cover to cover. To define your own workflow you need not start from hand-writing either — prefer letting the AI skill do it (next section), and keep the field details as reference.

### Generate definitions with the AI skill (recommended)

Writing stage/scope definitions does not require hand-writing field by field. The definition skill `create-workflow` is deployed into the harness; trigger it with natural language and it picks the mode automatically from your input:

| Mode | When it fits | Trigger example |
|---|---|---|
| Q&A mode (default) | Spot changes: adding a stage, creating a new workflow (scope), adding an approval gate to a workflow | "Add a risk-review stage to the existing workflow that reads the spec draft, produces a risk-review record, and hangs a manual gate" |
| Document mode | You already have a written process definition document (phases / stages / inputs & outputs / review gates / role tables); convert it wholesale into dmaf definitions | "Convert this process document into dmaf definitions" |

How the skill works: it gathers the business intent (Q&A mode asks everything in one round; document mode treats the document as the single source of truth and asks only one concentrated round of questions where things are genuinely ambiguous) → generates the definition files under `dmaf/workflows/` from templates (boilerplate fields, compile constraints, members and order all filled in automatically) → after confirming with you, runs `dmaf compile` to validate and fixes compile errors on its own. Your job is to answer the business questions (or provide the document), review the generated result, and commit `dmaf/compiled/`.

Prerequisite: the skill is deployed to the harness. `dmaf new` already writes the skill into the project's `dmaf/skills/` along with the skeleton (embedded in the engine and emitted from there); once `dmaf install --harness <name>` deploys it to the harness, it can be triggered. For existing projects that came in via `dmaf add` and never ran `dmaf new`, run `dmaf new --dir .` once to fill the gap. The skill is an engine slot and is not distributed with workflow packages. If the skill is missing you can still hand-write definitions: the reference sections from §2 on are kept for exactly that.

The daily loop (run in order after any definition or asset change):

```bash
dmaf compile                # definitions → compiled artifacts; all structural validation gates here
dmaf compile --check        # drift guard: confirm the committed artifacts match the sources
dmaf install --harness opencode   # deploy AI assets to the harness (ledger hash gate: unchanged targets auto-update; user-modified ones are skipped and reported)
dmaf check --harness opencode         # workflow references vs. actual harness content (defaults to the standard layout when no input selector is given)
dmaf doctor --harness opencode    # daily self-check: layout / artifact drift / manifest engine compatibility / reference completeness / asset drift
```

After changing definitions you only need to re-run `dmaf compile` and commit `dmaf/compiled/` (artifacts are byte-deterministic; the diff is the review). The default paths of commands like `dmaf compile` are the `dmaf/…` locations shown in the tree above; with no input selector, `dmaf check` defaults to the standard layout (`dmaf/workflows/{stages,scopes}`), so explicit arguments are usually unnecessary. Daily self-check routine: after git pull, run `dmaf doctor --harness <name>` — `would_change` means re-run install to sync; `modified` means a target the user changed; after confirming, add `--force`.

### Inline vs. standard directories

Both forms share the same parsing and semantics; choose by scale:

- **Standard directories** (`dmaf/workflows/stages/` + `scopes/`, via `dmaf compile`): workflows that need scope reuse, member governance, compile-time review, and artifact-diff review — **every evolving formal workflow uses this form**;
- **Inline single file** (`dmaf start --workflow <yaml>`): syntactic sugar for prototypes / experiments / minimal workflows. No artifact emission, not in the scope grid; new semantics get inline support automatically (sharing the parser with the standard directories).
- Inline and standard directories **share the same parser**; equivalence is continuously guarded by synthetic fixtures in the engine's tests (the repo samples are scope-only, with no inline definitions).

## 2. Stage definitions

> **This section through §8 is reference material**: when the AI skill (§1) generates definitions it observes these field constraints and compile rules automatically; the content here serves to proofread skill output, to debug against the compile error table, or to hand-write definitions when the definition skill is unavailable.

### 2.1 Files and naming

`dmaf/workflows/stages/<phase>/<slug>.md` — YAML frontmatter declares the structure; the body carries the execution instructions (written for humans to read, also serving as the agent's background context).

Two hard rules: **`id` must equal the file-name stem**; **`phase` must equal the name of the enclosing directory**. Getting either wrong is a compile error. phase is a pure classification label and takes no part in routing.

### 2.2 Frontmatter field table

| Field | Required | Description |
|---|---|---|
| `id` | ✓ | unique stage identifier, = file-name stem |
| `phase` | ✓ | = enclosing directory name |
| `collaboration` | ✓ | `single` (exactly 1 agent) \| `sequential` \| `parallel` (≥2 agents) |
| `agents` | ✓ | worker list, see 2.3 |
| `retry` | — | `max_attempts` (retry cap **after** the first attempt, `1` = 2 attempts in total), `on_exhausted: abort_workflow \| continue`; defaults 1 / abort |
| `approval` | — | when `required: true`, `gate` (gate name) must be given; on success the stage halts at `awaiting-approval` awaiting human disposition |
| `execution` | ✓ | `always` \| `conditional` (for conditional's skip semantics see §4) |
| `on_skip` | — | `skip` (default) \| `run`: when a hard-input producer is skipped, whether this stage propagates the skip or is dispatched as usual (§4 skip semantics) |
| `inputs` / `outputs` | — | declared inside the agents entries (full path templates), see §4 |

**A stage file must not carry scope fields** — "which stages this workflow contains" lives in the scope file.

### 2.3 Agent entry fields

```yaml
agents:
  - agent: architect                # agent name; must exist in the harness (agents/ assets)
    skills: [architecture-analysis]  # list of skill names; may be []
    inputs:                        # full artifact input paths: string = hard dependency; a mapping may declare required: false (soft input)
      - "deliveries/{SESSION_ID}/spec/{topic}-spec草案.md"
    watches: ["notes/{topic}-背景资料.md"]   # soft dependency (reading interest): parsed into the instruction payload, tolerated when missing, does not affect the topology
    outputs: ["deliveries/{SESSION_ID}/design/{topic}-hld.md"]
    task_description: "Based on the spec draft, produce the architecture design and ADR"   # supports {variable} templates; raw user input is carried only by the first stage via {TASK}; downstream stages consume only upstream artifacts
    vars: [product_line]           # optional: explicitly pick a subset from the session variable set (including constants), flattened into the action's vars field
```

Conventions: **outputs are promises** — at report time the Engine verifies the files exist, and any missing one is treated as a failure; **raw user input enters only at the workflow entry** — the reserved variable `{TASK}` is carried only by the first stage (intent-capture kinds) via its `task_description`; downstream stages consume upstream artifacts exclusively and never reference `{TASK}`, and the business short name serves only as the artifact file-name prefix; a stage with no output artifacts (the "submit to an external system" kind) declares `outputs: []` and is judged by the agent's report. The output format (markdown/json/pptx etc.) is agreed in the skill's execution instructions (the skill is the single source of truth for agent behavior); the protocol carries no format field.

### 2.4 Full example

```markdown
---
id: architecture-analysis
phase: design
collaboration: single
agents:
  - agent: architect
    skills: [architecture-analysis]
    inputs: ["deliveries/{SESSION_ID}/spec/{topic}-spec.md"]
    outputs: ["deliveries/{SESSION_ID}/design/{topic}-hld.md"]
    task_description: "Based on the spec, produce the architecture impact statement, design, and ADR draft"
retry:
  max_attempts: 1
  on_exhausted: abort_workflow
approval:
  required: true
  gate: architecture-review
execution: always
---

# Architecture Design

Produce the architecture design from the spec.

## Steps

1. Read the spec and the existing architecture baseline.
2. Produce the architecture impact statement, design, and ADR draft.
3. Wait for approval gate `architecture-review`.
```

## 3. Scope definitions

`dmaf/workflows/scopes/<name>.md` — **member claims + workflow-level metadata**. A stage claimed by no scope is inert (compiled into the graph, part of no workflow; the compiler emits an advisory).

The hard rule mirrors stages: **`name` must equal the file-name stem**; getting it wrong is a compile error.

```markdown
---
name: sdlc-standard
description: Three-phase workflow: requirements → design → development
vars:                                # business variable declarations (mapping form: name → inline default)
  topic:                             # empty value = required (start must provide it)
  constraints: ""                    # literal value = optional, inline default
constants:                           # constants: literal values, referencable from templates, always take the defined value (--var rejects them)
  product_line: "课件"
completion_template: |              # optional: delivery message template (§3.1)
  All done! Topic: {vars.topic}
  Deliverables: {outputs.spec-generation}
include_stages:                     # member claims (single source of truth)
  - intent-capture
  - spec-generation
  - …
---

# Body: workflow description (for humans)
```

**Two mandatory rules:**

1. **The `include_stages` order is the execution order** (the engine advances strictly serially in sequence order, one stage at a time); producers of hard inputs must be members and must precede their consumers — an order that violates a data dependency = compile error;
2. Referencing a nonexistent stage, or duplicate entries = compile error. The `depends_on` field has been removed: "who comes before whom" between stages is expressed by this sequence, and "who supplies data to whom" by hard-input full paths (the data dependency edges are derived automatically by the engine).

### 3.1 Delivery message template (`completion_template`, optional)

When the workflow reaches `complete`, the Engine renders `payload.completion_text` from this template and the Orchestrator **displays it verbatim** — the delivery message is declared by the definition rather than memorized by the orchestration prompt. Syntax (a dedicated renderer, not shared with the §4 artifact templates):

| Placeholder | Renders as |
|---|---|
| `{vars.<name>}` | session variable (including constants); name must be declared |
| `{outputs.<stage_id>}` | the output paths of all agents of that stage, joined with "、"; stage_id must be in `include_stages` |
| `{{` / `}}` | literal braces |

Rules:

- **Conditionals and loops are deliberately unsupported** — presentation templates do no logic; failure details are given structurally by `payload.summary.failed_actions`, which the Orchestrator relays mechanically;
- a placeholder referencing an undeclared variable or a non-member stage = **compile error** (inline workflows share the same semantics; `dmaf validate` gates it), so rendering never hits a missing key;
- omitting the field = the complete instruction carries no `completion_text`, and the Orchestrator falls back to relaying the summary.

## 4. Artifacts and template variables

- Artifacts are written in definitions as **full path templates** (project-root-relative, variables supported); the Engine renders them at dispatch time: `deliveries/{SESSION_ID}/design/{topic}-spec.md` → `deliveries/20261022-153000/design/课件-spec.md`. After rendering, only the last segment (the file name) is sanitized of illegal characters; directory segments are kept as-is.
- **Artifact paths are business semantics**: write your project's business paths; the common convention is `dmaf-output/{SESSION_ID}/<subdir>/` (the fixed prefix dmaf- avoids collisions with user-defined directories; work products must be committed — the engine never writes it into .gitignore), bucketed per session (one session's artifacts gather in one directory; re-runs never overwrite each other; sessions forked via `dmaf fork` likewise get their own buckets). **Never write into `.dmaf/`** — that is the engine-exclusive zone (session state and audit). Artifacts passed across stages: when the rendered path template of a consumer's inputs **equals** the rendered result of a producer's outputs, a producer-consumer relation forms (exact match on the full path; the same name in a different directory is a different artifact); an input with no producer is an external artifact, its path used as-is. Temporary files within a single stage are the skill's own affair (e.g. the system temp directory) and stay out of the delegation protocol.
- **Variable rules**: template variables must be ∈ the **scope declaration set** (names of `vars` ∪ `constants`) ∪ **engine-reserved variables**. Compile time gates against the union of all scope declarations; an undeclared variable is an immediate compile error. Common business variables (`topic`, `knowledge_point`, `constraints`, etc.) are supplied via `dmaf start --var` and declared in scope `vars`.

**Engine-reserved variables** (no declaration needed, injected by the mechanism; the engine has exactly these two built in):

| Variable | Description |
|---|---|
| `SESSION_ID` | session ID (a timestamp string, **live-bound on every render** to the current session directory name; not a path; commonly used for session bucketing of artifact paths or for deriving unique identifiers, e.g. `dmaf-output/{SESSION_ID}/…`, `course_{SESSION_ID}`). A session forked via `dmaf fork` has its own ID, the artifact bucket switches with it, and artifacts from before the fork point are copied by the engine into the new bucket |
| `TASK` | the user's raw requirement text (injected when provided via `start --task`; the workflow takes in natural-language input through it, and extraction belongs to the first LLM stage) |

**Composition of session variables**: there are only two declaration categories — business variables (declared in scope `vars`) and **constants** (declared in scope `constants`), plus the reserved variables (table above). At `dmaf start` the Engine composes them, in the order below, into **one** session variable set, shared alike by stage artifact templates, `task_description`, the delegation variable flattening, and §3.1's `{vars.*}`:

1. `constants` constants (literal values, always take the defined value);
2. `vars` inline defaults;
3. values provided via `--var k=v` (**only names declared in `vars` are accepted**, overriding same-named inline defaults);
4. the reserved variables `SESSION_ID` (always injected, and live-bound on every render to the current session ID — automatically points at the new session after fork), `TASK` (injected when non-empty).

A required variable = a name that is empty-valued in `vars` and not provided at start; if missing, startup is refused (exit code 3, reporting `缺少必须变量`). The business short name (e.g. the samples' `topic`) handles artifact naming inside stages — a division of labor distinct from `TASK`, which carries the raw requirement text. `--var` referencing a constant reports `常量不可通过 --var 覆盖`; names of the two declaration categories (`vars`/`constants`) are **mutually exclusive** and must not occupy reserved names — a violation = compile error. `derived_vars` has been removed — use `constants` for fixed literal values; for composite values, have the template reference the variable combination directly (e.g. `"{product_line}-{SESSION_ID}"`).

- Input/output templates with identical names matching exactly form a **producer-consumer relation**; producers of **hard inputs** must be members of the enclosing scope and precede the consumer (validated at compile time; the data dependency edges are derived automatically by the engine — no declaration needed). When a producer is not among the members (a lightweight workflow trimming away one design chain), the reference must be changed to a soft one.
- **Soft inputs** (`{ artifact: …, required: false }`) and **`watches`** (reading interest) carry no closure requirement; inputs known to be missing are listed in the instruction's `missing_inputs` field (advisory).
- **The delegation payload (`delegation`) is pre-built by the Engine**: each action of a dispatch instruction carries a ready-made delegation JSON, and the Orchestrator forwards it verbatim to the subagent, assembling nothing. **The path fields share the stage definition's names** (`inputs`/`outputs`; the values are the full paths obtained by resolving the name templates, always present, an empty array meaning none — the single path of a single-output stage is the write target), so what the definition declares is exactly what the agent receives, with no second vocabulary to memorize; the remaining protocol fields are `role`/`task_description`/`revision_feedback` (the latter appears only in revision loops). Workflow variables are flattened into top-level fields according to **the full session vars set (including constants) ∪ the subset picked by that agent's `vars:` declaration (going into the action's `vars` field)** — constants appear in the session message; on conflict with a same-named protocol field, the protocol field wins. When an upstream result needs to be consumed downstream, go through the `inputs`/`outputs` artifacts (the file is the promise); there are no summary-type special variables. The field set is fixed by the engine (independent of stage configuration); the spec is `docs/schemas/delegation.schema.json`, and the sample agents (`dmaf/agents/*.md`) are living examples of the protocol.
- **Skip semantics**: an agent reports `status: skipped` (must attach a non-empty `reason`) → the stage is recorded `[S]`; downstream stages whose hard-input producer was skipped **propagate the skip** by default (audited level by level), and `on_skip: run` exempts; `execution: conditional` is a declarative annotation of "may skip" (a hard-input producer may not be conditional-only — intercepted at compile time). `skipped` is a resolved terminal state: a skipped stage **does not block workflow progress** — "on-demand" stages are written into the scope sequence to express ordering, and downstream stages reference their artifacts via soft inputs (absence lands in `missing_inputs`); within the same stage, a later sequential agent soft-references the earlier agent's artifacts for the handoff (legal — the dead-wiring check exempts the stage itself).

## 5. Approval gates and revision loops

A stage with `approval.required: true` halts at `awaiting-approval` after completion:

```
Generation done → awaiting-approval → human approves (granted) → completed → downstream
                             ↘ human rejects (rejected) → revising → automatic re-dispatch
                                 (the revision dispatch carries revision_feedback = rejection notes; unlimited rounds)
```

Gate names are unique within the workflow by convention (the engine does not check for duplicates — it is the name by which humans and agents identify "which gate", e.g. `outline-review`). The revision loop is orchestrated automatically by the Engine: after a rejection, the next `next` comes back with `revision_feedback` and re-dispatches the same agent.
**Reviewer (optional)**: `approval.reviewer: <agent>` hands the disposition to a designated agent for pre-review — the `await_approval` instruction carries the reviewer together with the list of deliverables it should review; the Orchestrator dispatches the reviewer and then files the approval report with its conclusion; audit shards record the reviewer's provenance. The default (no reviewer written) is human disposition.

## 6. Retries and parallel aggregation

- `max_attempts` is the retry cap **after the first attempt**; on failure the Engine records a `retry.scheduled` audit shard and automatically re-sends on the next hop (new action_id, attempt+1).
- A stage with `on_exhausted: continue`: after retries are exhausted it does not block the workflow, and missing items are not removed from downstream inputs (downstream handles missing artifacts itself).
- **Parallel/sequential aggregation**: each agent's last attempt is the one that counts — a successful retry erases earlier failures.

## 7. Workflow pattern support and design trade-offs

The Engine's execution model is a deliberately narrowed algebra — four mechanisms combine into all of its expressive power:

| Mechanism | Semantics |
|---|---|
| Serial advance in sequence order | scope members execute in `include_stages` sequence order (**order is execution order**), **only one stage dispatched at a time**; an in-flight stage blocks the rest — the engine has no stage-level parallelism |
| Intra-stage orchestration | `collaboration: sequential / parallel`: parallelism happens only among the multiple agents inside a stage (aggregation rules in §6) |
| On-demand resolution | `execution: conditional` self-assessed skip + propagated skip (§4) — what actually advances at runtime is the compile-time graph's remaining sequence after skip resolution |
| Gate revision loop | reject → revising → re-dispatch carrying `revision_feedback` (§5); re-entry is confined to this stage |

**Common workflow patterns:**

| Pattern | Supported | How to express |
|---|---|---|
| Linear pipeline | ✓ | the topological order is the workflow |
| On-demand branching (a step may not apply) | ✓ | conditional + `skipped`: audit trail; on-demand skips set no gate |
| Mutually exclusive routing (two exclusive paths, each with its own downstream) | weak | no graph-level branching mechanism: merge into a single stage and let the agent judge internally — branch decisions go to the agent, and the structure stays unique from the engine's point of view |
| Parallel progress on independent work | limited | merge into the same stage as parallel agents (sharing gate and retry policy), or serialize; no stage-level parallelism |
| Set fan-out (task-by-task / module-by-module processing) | ✓ (absorbing) | a breakdown stage + an item-by-item loop inside the execution stage (the samples do exactly task-breakdown → atomic-execution); audit granularity stops at the stage, and task-level trails live in the artifact documents |
| Single-point revision iteration | ✓ | the gate revision loop |
| Cross-phase iteration (defect → fix → retest) | ✗ | deliberately unsupported: append-only audit has no back edges. Defects go honestly into the report and to a gate (e.g. `pr-review`) for human adjudication; code fixes take the next session or a `fork` (the audit naturally separates rounds) |
| Human in the loop | ✓ | any stage can carry an approval gate |
| Event/scheduled triggers, dynamic structure, sub-workflow nesting | ✗ | out of domain: orchestration is pull-based, and every `next` step is a pure function |

**The root of the trade-offs** is three engine principles, and they shape the expressive power:

1. **Determinism** — `next` is a pure function (no clock / random / IO): the dumber the graph, the cheaper `verify-determinism` / `replay` / `fork` (under linear advancement a fork point has at most one in-flight stage, so fork semantics are trivial);
2. **Audit first** — the append-only hash chain cannot be rewritten, hence no cross-stage back edges and no global completed→revising re-entry;
3. **Layered complexity** — structural determinism stays with the engine (linear advancement + fixed aggregation rules); judgment noise goes to the agents (internal loops, exclusivity decisions, `skipped` self-assessment). The stage is the audit unit: the more iteration absorbed into a stage, the coarser the audit granularity — a deliberate exchange, and in the right direction.

**The workflow author's criterion**: if the requirement decomposes into the four mechanism layers in the tables above, express it in definitions; if it does not, first ask whether it belongs to this domain (AI-native SDLC-style deterministic delivery workflows). The sample library is the model to follow: by data flow, hifi-ue and architecture-analysis could run in parallel, yet the samples choose serial (UE goes first, feeding the architecture judgment); detailed-design merges the frontend and backend llds into one parallel stage sharing a single gate. When in doubt, prefer "merge stages / serialize / a new session per round" over counting on the engine to grow new control flow.

## 8. Compile error reference table

| Error message (excerpt) | Fix |
|---|---|
| `工件模板 '…' 引用未知变量 '{x}'` | Undeclared variable: add it to scope `vars` (or it is a constant/derived/reserved variable, §4) |
| `stage 'X' 的输入 '…' 没有任何 stage 的 outputs 能提供` | No producer: add a stage that produces it; for an existing external file, switch to a soft-input reference (`required: false`) |
| `stage 含 depends_on 字段（已移除）` | Write the execution order into the scope's include_stages sequence; data dependencies are expressed by hard-input full paths (producers derived automatically) |
| `…的硬输入 '…' 的生产者 'Y' 不在成员序列中` | Bring Y into the scope members ahead of the consumer, or change the input to a soft reference (`required: false`, the on-demand trimming form) |
| `…的生产者 'Y' 均排在 stage 'X' 之后——生产者必须排在消费者之前` | Adjust the include_stages order: producers before consumers (order is execution order) |
| `…的软输入 '…' 的生产者 'Y' 排在其后——…（死接线）` | Under a linear execution order this input would be missing forever in this session: adjust the order, or have it provided by a non-member / externally |
| `…由本 stage 自己生产（疑似定义错误）` | Input and output share the same name; change it |
| `stage id 'X' 与文件名 stem 'Y' 不一致` | Fix the id or the file name |
| `phase 'X' 与所在目录 'Y' 不一致` | Move to the matching directory or fix phase |
| `stage 'X' 声明了 scopes` | Delete it; membership goes into the scope file's include_stages |
| `completion_template 占位符 '…' 引用未声明的变量/stage '…'` | Add the variable to scope vars/constants, or the stage to include_stages (§3.1) |
| `scope 'X' include_stages 条目 'Y' 在 stage 库中不存在` | Fix the slug or create the stage file first |
| `stage id 重复` | Change the id (the sequence has no cycles: execution order = the written order of include_stages) |
| `collaboration=single 时 agents 必须恰好 1 个` | Trim to 1 or change collaboration |

## 9. AI assets (agents / skills)

- `agents/<name>.md`: frontmatter `name` (unique), `mode` (`primary` | `subagent` | `all` — workflows may only reference `subagent` | `all`; `primary` cannot be dispatched; validated by `check`), `description` (non-empty); the body states responsibilities and conventions.
- `skills/<name>/SKILL.md`: frontmatter `name` must equal the directory name; may carry resources such as `scripts/`.
- Deployment and validation loop:

```bash
dmaf install --harness opencode     # standard directories → harness (ledger hash gate, see below)
dmaf check --harness opencode       # workflow references vs. actual harness content (defaults to the standard layout when no input selector is given)
```

`--harness` takes a name, which the engine resolves to a directory under the project root: `opencode`→`.opencode`, `claude` (alias `claude-code`)→`.claude`, `zcode`→`.zcode`, `cursor`→`.cursor`, `gemini` (alias `gemini-cli`)→`.gemini`; `codex`→`.codex`, `dsh`→`.dsh` (agents in these two layouts are converted to TOML automatically). Path-like values (containing separators or starting with `.`) are passed through as the flat-md layout; unknown bare names error out (exit code 2).

**install has ledger hash gate semantics**: `dmaf-installed.yaml` at the harness directory root records the fingerprint the engine wrote for each target — a missing target is installed (installed); unchanged ones **auto-update** when the sources are upgraded (updated); user-modified ones are **skipped** and reported (skipped); `--force` overrides explicitly (overwritten). `--prune` clears orphans — any entry whose name is not in the package source is swept (judged by the name list, not the ledger); locally hand-placed skill directories will be deleted, so use with care; `--check-only` is a read-only checkup.

- Agents/skills **not** in the reference inventory (e.g. the sdlc-* of the scope-ified samples) are listed by `check` — that is a deployment-time hint; at runtime a missing skill is an execution error: agent fails → report failed → repair the harness → run `next` again on the same `--session` to resume.

## 10. Minimal end-to-end example

Take "add a risk-review stage to an existing workflow" as the example. Going through the AI skill, one sentence to `create-workflow` — "add a risk-review stage that reads the spec draft, produces a risk-review record, and hangs a manual approval gate" — is enough: it generates the file, back-derives the membership and sequence position, and runs the compile; the handwritten steps below show what it does on your behalf:

1. Create `dmaf/workflows/stages/design/risk-review.md` (inputs: the spec draft; outputs: the risk-review record);
2. downstream stages add its outputs to their inputs (data dependencies are expressed by inputs), and the scope `include_stages` sequence places it ahead of its consumers;
3. `dmaf compile` → once it passes, commit `dmaf/compiled/`;
4. `dmaf check --harness <name> …` confirms the referenced agents/skills are deployed;
5. run a session, and the new stage appears in the plan.

## 11. Command quick reference

| Command | When to use |
|---|---|
| `dmaf new [--dir .]` | one-time project setup: fill in the standard layout (never overwrites existing files) |
| `dmaf compile` / `--check` | after every definition change; the artifact diff is the workflow-change review |
| `dmaf install --harness <name>` | after every agents/skills change |
| `dmaf check --harness <name>` | after deployment / in CI: workflow references vs. actual harness content (standard layout by default) |
| `dmaf doctor --harness <name>` | daily self-check: layout / drift / manifest compatibility / reference completeness / asset drift |
| `dmaf start --scope <name>` / `dmaf start --workflow <f>` | start a session |
| `dmaf next / report` | the orchestration loop |
| `dmaf inspect / log / verify-audit / replay / fork / cancel / verify-determinism` | session operations |
| `dmaf validate --workflow <f>` | inline workflow structural validation |
| `dmaf add --from <source>` / `dmaf push <target>` | install / deliver workflow packages (same merge core; add also accepts market entry URLs) |
| `dmaf auth login / logout / status`, `dmaf publish` | market sign-in state and publishing |

Deep-water material (all in the engine repo; `dmaf new` does not distribute them to user projects along with this guide): the engine manual (command details, `docs/engine-manual.md`) and `docs/phase-stage-scope.md` (the sample inventory of this repo).
