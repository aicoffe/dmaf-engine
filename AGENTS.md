# AGENTS.md

**Generated:** 2026-10-22 (v0.5.0, definition-layer/runtime-layer layout finalized; SESSION_ID live binding + fork artifact isolation); updated to v0.6.0 on 2026-11-12 (scope sequencing: `depends_on` removed, `include_stages` order IS the execution order); v0.7.0 (i18n: `DMAF_LOCALE` / `start --locale` / locale baked into sessions + bilingual guide embedded in scaffold written per locale)

User docs live in `docs/` (English by default, Chinese under `docs/zh/`); internal dev archive: `docs-dev/` (gitignored, not published). All configurable environment variables are listed in `.env.example`.

## Overview

D-MAF engine — a standalone project implementing a deterministic multi-agent routing engine in **Rust**. Core principle: **the Engine is the only routing authority; agents are controlled execution units**. `next` is a pure function — the same state always yields the same instruction. Single binary `dmaf`; session state and audit live entirely on disk; **zero harness dependency at runtime**.

Repository = engine + sample. The dmaf project layout has two layers: the **`dmaf/` definition layer** (`workflows/`, `agents/`, `skills/`, `hooks.yaml`, `docs/`, `compiled/`, all committed) and the **`.dmaf/` runtime layer** (engine-exclusive session state and audit, gitignored). Workflow artifacts never enter the engine area — full paths are written directly in stage `inputs`/`outputs` (with `{SESSION_ID}` session bucketing). This repository's content is the AI-native SDLC standard-flow sample (scope definitions + AI assets); user projects mirror the sample's structure.

## Commands

```bash
cargo build --release                  # produces target/release/dmaf (cargo package dmaf-engine)
cargo test                             # 191 tests (all offline; incl. i18n catalog alignment / locale baking / help key guard / system-locale detection parsing, 10 cases); must be all green, determinism tests especially

# Engine install (user machines; no repo source needed; rerunning the same command upgrades in place)
curl -fsSL https://dmaf.aicoffe.com/install.sh | sh   # macOS / Linux (--source github selects the source)
irm https://dmaf.aicoffe.com/install.ps1 | iex        # Windows PowerShell
npm i -g @aicoffe/dmaf-engine                                # npm channel (all platforms)

# One-off project operations (user-repo perspective)
dmaf new --dir my-project                   # greenfield: scaffold a project skeleton (only template: minimal; embeds the definition skill into dmaf/skills/); install the runnable sample via dmaf add
dmaf new --dir . [--force]                  # brownfield: complete the standard layout in an existing repo (never overwrites existing files; missing definition skill is filled in too)

# Compile & deploy (after definition/asset changes)
dmaf compile                           # dmaf/workflows/ -> dmaf/compiled/ (byte-deterministic artifacts, committed)
dmaf compile --check                   # drift guard: byte-for-byte compare of sources vs committed artifacts
dmaf install --harness opencode       # dmaf/agents, dmaf/skills -> harness (idempotent sync; --prune removes orphans; --check-only is read-only)
dmaf install                          # default --harness: auto-detect harness dirs at project root (lists several; --harness all installs everything); also places dmaf/harness/<name>/ entry configs
dmaf install --harness codex          # TOML-layout harness: agents converted to TOML (same for dsh)
dmaf check --harness <name> (--workflow <f> | --session <dir> | --stages <d> --scopes <d>)  # harness binding validation (defaults to the standard layout when no input source is given)
dmaf validate --workflow <file>.yaml   # inline workflow structure validation (the sample is scope-only, no inline definitions)
dmaf add --from ../dmaf-sdlc          # workflow package -> current project (ledger-hash-gate merge + recompile + chained install; --dry-run reports only; --force overwrites target-side changes, chained install force-overwrites user changes inside the harness too)
dmaf add https://<market>/<userid>/<project> [--tag <version>]   # market entry install: anonymous fetch -> digest double-check (fail closed) -> safe unpack -> same merge core (defaults to latest; ledger records the actual version and hosted digest; local --from .tar.gz goes through the same safe unpack)
dmaf auth login --token <dmafmt_…> [--market <base>]   # market login: format precheck -> GET /api/me validation -> credentials stored in the user-level config dir (logout/status in the same group)
dmaf publish [<dmaf dir>] [--project] [--version|--bump] [--intro <file>] [--github-url] [--market <base>] [--dry-run]   # publish: compile + doctor gate (rejects on errors only) -> local precheck (E-9 foreign-package file exclusion) -> deterministic packaging -> multipart upload (409 bumps the version and resends; publish-only: no update/overwrite/takedown)
dmaf push ../xx-game                  # deliver the current workflow project (must be validated) to a target project (mirror of add, same merge core)

# Runtime (zero harness dependency)
dmaf start --scope sdlc-standard --task "<requirement text>" --var topic=<short-name>   # scope mode: requirement text goes to TASK; required vars via --var k=v
dmaf start --workflow <id> --task "…" [--var k=v]                        # inline mode (dual-track retained by the engine; test fixture in tests/fixtures/)
dmaf next --session .dmaf/<dir>        # next-hop instruction (JSON)
dmaf report --session .dmaf/<dir> --payload <file|->
dmaf doctor                            # environment checkup (read-only): layout / .dmaf hygiene / artifact drift (incl. version compatibility) / manifest engine compatibility / harness completeness + asset sync drift
dmaf inspect / log / verify-audit / replay / fork / cancel / verify-determinism --session …
```

Requires the Rust toolchain (rustup 1.85+); the repo ships its own `.cargo/config.toml` (USTC sparse mirror overriding a broken global source; **the USTC mirror 404s on some cargo-client requests (curl on the same URL works) — when cargo install hits it, switch to the rsproxy mirror: `cargo --config 'source.crates-io.replace-with="rsp"' --config 'source.rsp.registry="sparse+https://rsproxy.cn/index/"' install <crate>`**). No linter; CI is GitHub Actions (cargo build/test + compile --check); releases are tag-triggered through the dist pipeline (`.github/workflows/release.yml`, dist 0.34; artifact naming frozen to dist's actual shape: `dmaf-engine-<target>.tar.xz/.zip` + `sha256.sum` + same-named `.sha256`, see docs-dev/引擎安装与分发实施方案.md §6.1).

**Harness name mapping**: `--harness` takes a name (shared by install/check/doctor/compile); the engine resolves it to a directory and layout under the project root: `opencode`→`.opencode`, `claude` (alias `claude-code`)→`.claude`, `zcode`→`.zcode`, `cursor`→`.cursor`, `gemini` (alias `gemini-cli`)→`.gemini` (flat-md: md files copied as-is); `codex`→`.codex`, `dsh`→`.dsh` (toml-agents: agents converted to TOML, `mode` preserved as a `# dmaf-mode:` comment); skills are always copied as whole directories (source side supports one level of category subdirs `skills/<category>/<skill>/`; **opencode and cursor support nested discovery** — install keeps category paths, other harnesses flatten by skill name; skill names must be globally unique). Path-like values (containing separators or starting with `.`) pass through as flat-md; unknown bare names error out (exit code 2).

## Key Conventions and Pitfalls

- **Two-layer boundary**: `dmaf/` = definition layer (committed, incl. compiled/); `.dmaf/` = runtime layer (whole dir gitignored, engine-exclusive). **Business artifacts never go into `.dmaf/`** — full paths are written directly in stage `inputs`/`outputs` (project-root relative, `{SESSION_ID}` session bucketing supported); producer-consumer pairs match exactly on rendered paths; agents create directories as needed when writing files.
- **Zero harness dependency at runtime**: start/next/report etc. never read `.opencode` or the registry; the instruction action carries a `skills` list (no skill_brief). A missing skill = harness execution error -> report failed -> user fixes -> resume. Reference integrity is validated at deploy time by `dmaf check --harness`.
- **`.dmaf/<session>/` is the Engine-exclusive zone**: agents/prompts must never read or write it; the session dir contains only engine bookkeeping (dmaf-state.md, audit/, last-report.json). `doctor` checks `.dmaf/` hygiene (non-timestamp entries = external encroachment). Top-level project-root directories (workflows/agents/skills/hooks.yaml/dmaf-output etc.) belong to the user — the old v0.3 layout is long retired, and business artifact directories (like the sample's `dmaf-output/`) are perfectly legitimate; the engine makes no "leftover" judgments.
- **Determinism**: `instruction_id` derives from the audit sequence number; `compute_next` must not introduce clock/randomness/IO (`tests/test_determinism.rs` guards with randomized-trace regression).
- **Audit first**: write the audit shard, then save state; the append-only hash chain is immutable.
- **Compile loop**: changing `dmaf/workflows/` requires recompiling and committing `dmaf/compiled/`; `dmaf compile --check` guards drift; artifacts must never be hand-edited.
- **The definition layer is the single source of truth**: `dmaf/agents/`, `dmaf/skills/` changes are synced via `dmaf install --harness <name>` — never manual cp, never hand-edit harness dirs. install has **ledger-hash-gate** semantics: `dmaf-installed.yaml` at the harness dir root records write-time fingerprints — untouched targets auto-update with the source (updated), user-modified targets are skipped (skipped) and reported, `--force` overrides explicitly (overwritten); per-file for agents/entry configs, whole-directory for skills.
- **Entry configs & project manifest (optional)**: files under `dmaf/harness/<name>/` are placed by install **file-by-file inside the harness directory** (e.g. `.opencode/opencode.json`, never the project root), under the same ledger hash gate; no secrets in this directory. `dmaf/manifest.yaml` declares package identity and the `engine` version range (e.g. `">=0.5,<0.6"`); doctor checks binary compatibility against it. Daily self-check routine: git pull -> `dmaf doctor --harness X` (`would_change`: rerun install to sync; `modified`: user-modified targets — confirm, then add `--force`).
- **Package distribution (add/push)**: the merge core lives in `src/package.rs`; the two commands differ only in direction and push's validation gate. Package files exclude project-owned slots (`dmaf/manifest.yaml`, `dmaf/README.md`, `dmaf/docs/流程定义指南.md`, **`dmaf/packages.yaml`** — the local ledger records the publisher's absolute-path source; distributing it would make any installer with an existing ledger see a conflict, and publish benefits likewise; plus the definition-skill dir `dmaf/skills/create-workflow/` shipped by dmaf new — a generic skill name distributed with packages would collide across packages in multi-package market installs, so each project's copy is self-held by the engine skeleton) and `dmaf/compiled/`. Merging follows the **hash gate** of `dmaf/packages.yaml` (engine ledger, never hand-edit): target unchanged -> updatable; user-modified -> conflict and **nothing is written at all** (add/push `--force` overrides explicitly: user changes are not kept, an overwritten list is reported, the ledger re-records with the new hash; `--force` also applies to the chained install — the install hash gate force-overwrites user changes inside the harness too); a merge is always followed by a recompile. Publishing naming convention: agent/skill/scope names are prefixed with the package name.
- **Market integration (auth/publish/add entry URLs, v0.5.4)**: sole semantic basis is the internal market guide and openapi contract (docs-dev/, contract v0, pre-G1-freeze). Four invariants: archive unpack = a project root directly mergeable via `dmaf add --from` (published archives restore `dmaf/manifest.yaml` outside package_files); packaging determinism (server-side byte SHA-256 decides idempotency/conflict); install side fails closed (`X-Content-Digest` double-check + safe unpack, zero writes on violation); command output is the only channel for rejection reasons. Address resolution: `--market` > `DMAF_MARKET_URL` > credentials file `[default] market` > built-in default (official instance `https://dmaf.aicoffe.com`); https only (plain http for localhost only); credentials live in the user-level config dir keyed by base (Windows `%APPDATA%\dmaf\credentials.toml`); `DMAF_MARKET_TOKEN` is a temporary override, never persisted, token displayed as first 12 chars only; error-envelope mapping to exit codes (400/401/403/404->3, 409->4, 429/5xx/network->5; `content_integrity_violation` forbids retry, retryable errors retry with same-byte backoff up to 3 times); the publish gate reuses `cli::doctor_core_checks` (errors reject only, E-3); the ledger's market source records `digest` and the actual version tag. The conductor's one-line publish flow (login guidance -> generate `dmaf/intro.yaml` -> publish -> receipt) is in `dmaf/skills/dmaf/SKILL.md` §5.5.
- **Stack binding (sample mechanism)**: neutral specs + built-in stack skills under `dmaf/skills/stacks/` (backend rust/go/java, frontend vue3-naiveui/react-mantine; SKILL.md entry + reference/ routing, reference files always carry trigger conditions); `architecture-analysis` has three modes (selection advice / identification confirmation / verification) and produces the project stack declaration `dmaf-output/tech-stack.md` through the approval gate (one of the stage outputs, session-independent artifact). Neutral skills after architecture carry a uniform "stack binding" preamble in their header and dispatch four ways per the declaration (binding present -> load the stack skill / binding "none" -> generalized execution with verification commands per the declaration / undeclared -> neutral execution / unparseable -> report as-is); stacks outside the manifest are surfaced at the gate, default generalization forbidden; stack knowledge converges at a single point (mechanism docs in docs-dev/).
- **`retry.max_attempts` counts retries after the first attempt** (`1` = 2 attempts total); stage aggregation takes each agent's most recent attempt.
- **`dmaf/hooks.yaml` (project-level hooks, optional)**: the engine only invokes them in configuration order — the init point (before start creates the session) + after each audit shard is written, matching event_type against the `on-event` table — never reads results, never records trace; hook commands are relative to the project root (CWD); hook stdout is forwarded to engine stderr, leaving the engine stdout contract (pure JSON) undisturbed; `--no-hooks` / `DMAF_NO_HOOKS=1` disables. Ledgers with and without hooks are byte-identical; a hook breaking determinism is the user's responsibility (contract design in docs-dev/).
- **Delegation payloads and delivery copy are built by the Engine**: the dispatch instruction's action carries `delegation` (the conductor forwards it verbatim, never assembles one); scope/inline can declare `completion_template` rendered into `completion_text` — the conductor prompt carries no business copy (design in docs-dev/). **Two language channels**: the protocol channel (conductor->subagent) forwards verbatim; the presentation channel (conductor->user) always uses the language of the user's most recent message, and engine-rendered copy reaches the user only as faithful paraphrase — information complete, nothing added or dropped, technical identifiers verbatim (red lines in `dmaf/skills/dmaf/SKILL.md` §6; producer language policy in each agent definition's "language policy" section).
- **Template variable `SESSION_ID`**: the session ID (timestamp string, not a path), used for session bucketing of artifact paths; artifact paths are no longer injected into templates (v0.3's SESSION_DIR removed). **Live binding at render time (v0.5.0)**: `router::effective_vars` makes it always equal the current session ID (`session_dir` basename); the value baked into `state.vars` at start is record-keeping only — artifact paths, delegation flat vars, delivery summaries, and report's expected-artifact validation all go through this one entry point; new render sites must not clone `state.vars` directly.
- **Two variable classes (v0.4.0)**: scope declarations have only `vars` (mapping form: empty value = required, literal = inline default) and `constants` (fixed literals, referencable from templates, rejected by `--var`); the two names are mutually exclusive and must not occupy reserved names (`SESSION_ID`/`TASK`); `defaults`, `derived_vars`, `description_from_stage` are all removed (misuse gets a migration hint); GRID_VERSION = 5 (scope-grid: vars as mapping, constants, `include_stages` ordered = execution order, `depends` compile-time derived data-dependency edges). User raw input enters only at the flow entry: only intent-capture (the first stage) consumes it via its `task_description` (template `需求原文「{TASK}」` — "requirement text: {TASK}"); downstream stages consume only upstream artifacts, never `{TASK}`; the business short name (topic) is only an artifact filename prefix.
- **Scope sequencing (v0.6.0, breaking change)**: the `depends_on` field is removed (leftovers get a migration error) — a scope's `include_stages` **order IS the execution order** (compute_next iterates the sequence, strictly serial stage-level progression). Data dependencies are expressed by hard inputs, with derived edges computed at compile time (`workflow::validate_and_derive_sequence`; graph v3 carries no author dependencies) consumed by deps_terminal and the dispatch assertion (`router::assert_hard_inputs_ready`, purely defensive). Compile validation switched rails: a hard input's producer must be a scope member ordered before the consumer; dead-wired soft inputs/watches (no member producer precedes the consumer, so under a linear order they would necessarily be absent forever) are blocked as compile errors — the intra-stage sequential handoff of a stage's own outputs is exempt; a producer outside the membership = legitimate pruning-on-demand (the light-flow-trims-design-chain shape). Scope pruning is no longer hostage to the dependency closure: the light bugfix path = the `sdlc-bugfix` scope (7 members) + soft references to plan/atomic/systest design artifacts (plan takes spec v1 as an inevitably hard baseline). Design and decision records in docs-dev/.
- **Approval gates (scope/inline can both declare)**: the sample sdlc-standard has nine gates — intent-accept / spec-review / ue-review / architecture-review / hld-review / lld-review / design-accept / plan-review / pr-review. Stopping at `awaiting-approval` is by design; `rejected` enters a revision round (dispatch carries `revision_feedback`); the conductor must never make approval decisions on the user's behalf (no answer = stays at the gate; retired approach in docs-dev/).
- **Fork: the fork point must have no in-flight action**; the source session stays read-only and untouched. **The forked session's artifact buckets switch to the new session ID via the SESSION_ID live binding**: artifacts of actions completed before the fork point are copied from the source bucket to the new bucket (the result JSON's `copied_artifacts`/`missing_artifacts` list new-bucket paths), and the two branches write their own buckets from then on, never overwriting each other; paths without `{SESSION_ID}` stay at the same location on both sides (session-independent artifacts, shared by the branches, existence-confirmed only). Sessions forked before v0.5.0 still write the source bucket under the old semantics — to isolate, fork again from the source session. Never hand-edit `dmaf-state.md` vars (covered by the audit hash chain; verify-audit will fail). Existing sessions on the old `output/` layout are not migrated but remain usable (`--session` explicit path).
- Engine instructions/reports are pure JSON (stdout UTF-8, errors on stderr); exit codes 0/2/3/4/5.
- Human-facing text is bilingual (v0.7.0 i18n): defaults to the system language (zh-family -> zh, everything else -> en; detection failure falls back to en), with `DMAF_LOCALE`/`start --locale` as explicit locks. **Locale is a session fact** — start bakes it into dmaf-state.md, session commands read the session not the env (old sessions fall back to zh), fork inherits the source session, no mid-session hot-switching. Catalogs live in `src/i18n/catalogs/` (key alignment enforced by tests); clap help (--help/-h/value_name) is catalogized in the M3 follow-up batch (`help.` group + `t_static` static references; locale preset from DMAF_LOCALE before parsing; key completeness guarded by tests).

## Environment Variables

| Variable | Purpose | Default |
|------|------|------|
| `DMAF_NO_HOOKS` | Set to 1 to disable dmaf/hooks.yaml hooks (per-command `--no-hooks` flag also exists) | unset |
| `DMAF_LOCALE` | Human-facing text language (`zh`/`en`; two stages: preset at run entry (this var > system-locale detection: zh-family -> zh, otherwise en), then `start --locale` and session baking override — session commands read the session, not the env) | unset (system-locale detection, en fallback) |
| `DMAF_MARKET_URL` | Market address (resolution order: `--market` > this var > credentials file `[default] market` > built-in default) | `https://dmaf.aicoffe.com` |
| `DMAF_MARKET_TOKEN` | Market PAT temporary override (CI, never persisted; takes precedence over the credentials file) | unset |
| `DMAF_CREDENTIALS_FILE` | Explicit credentials file path (tests/CI; defaults to the user-level config dir `%APPDATA%\dmaf\credentials.toml` / `~/.config/dmaf/credentials.toml`) | unset |
| `DMAF_INSTALL_DIR` | Install directory for the dmaf binary (install.sh / install.ps1) | `~/.local/bin` (sh) / `%LOCALAPPDATA%\Programs\dmaf` (ps1) |
